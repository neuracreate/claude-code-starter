# CLAUDE.md

這份檔案是你跟 Claude 的協作規則。Claude 每次開始工作前都會讀它。

放在 `~/.claude/CLAUDE.md` 就是全域規則，所有專案都吃得到。放在某個專案資料夾裡，就只有那個專案吃得到。

**這是一份起手版，改它就對了。** 用一陣子之後你會發現有些習慣沒寫進來，補上去；有些規則你根本不在意，刪掉。這份檔案越貼近你真實的工作方式，Claude 就越好用。

---

## 1. 怎麼跟我說話

用繁體中文回覆。

先給結論再展開細節。段落分好，不要密密麻麻。優先用段落表達，需要對照或比較時才用表格與條列。

不要客套，不要加沒必要的免責聲明。直接、清楚、能執行就好。

---

## 2. 動手前先講思路

**不要一次做一大堆事。** 每個重要動作前先說明三件事：打算怎麼做、為什麼這樣做、預期產出是什麼。等我確認方向再動手。

改一個變數名這種小事直接做。只要牽涉多個檔案、多個步驟、或不可逆的變更，一律先講。

**複雜任務拆成階段。** 先列出階段，每完成一個停下來讓我確認，再進下一個。不要跳著做，也不要一口氣塞完。

**建議要有依據。** 不要用「感覺」、「應該」、「通常」這種沒有支撐的說法。提出方向時要講清楚依據是什麼、來源在哪、有多確定。手上證據不夠就直說「這個我沒把握」，不要用模糊語言帶過。

## 4. 這些事先問過我

做之前一定要停下來說明、等我確認：

- 刪除檔案或資料夾
- 一次改超過三個檔案
- 安裝新套件
- 改設定檔（`.env`、`package.json` 這類）
- 任何 `git push`、`git reset --hard`、覆寫遠端的操作
- 資料庫的結構變更或刪資料
- 呼叫要付費的 API，先告訴我大概多少錢

這些可以直接做，不用問：

- 讀檔、列目錄、查 log
- 在暫存檔上做實驗
- `git status`、`git diff`、`git log` 這類只是看的指令
- 跑測試、lint、build

**commit 前先讓我看 diff**，用中文簡短說這次改了什麼、為什麼。commit message 用中文寫。

不確定的時候，選「先問」不要「先做」。

## 5. 檔案放哪

**一開始不要分類。** 東西都放在同一層，一個資料夾一個用途，這樣就好。

分類是等到「東西多到找不到」才做的事。太早分類的下場是三個空資料夾擺在那裡，你還得記住每個是幹嘛的。

### 什麼時候該把東西搬出來

判準只有一句：**這東西有沒有自己的生命週期？**

白話講就是——它會不會自己動、會不會被別的東西依賴、壞掉的時候會不會有人來找你。

| 你發現 | 它其實是 | 搬到 |
|---|---|---|
| 你會一直回來改它，有自己的 git | 產品 | `products/` |
| 要 24 小時開著（聊天機器人、監聽服務） | 常駐服務 | `bots/` |
| 被別的程式叫來跑一次，跑完就結束 | 任務 | `jobs/` |
| 按時間自己跑（每天備份、每週抓資料） | 排程 | `schedules/` |

**四個不用一次建完。** 第一次出現符合條件的東西，才建那一個資料夾。你可能永遠不需要 `bots/`，那就別建。

> **給 Claude 的指示**：使用者要開新東西時，先確認這是用完就丟的，還是要長期維護的。要長期維護、而且符合上表任一條的，主動建議放進對應資料夾並說明理由。如果使用者現有的東西已經符合條件卻還放在根目錄，可以提醒一次，但不要每次都講。

### 每個資料夾裡面

**產物、暫存、過程截圖一律進該資料夾自己的 `.scratch/`。** 不要放在資料夾根目錄，更不要放桌面。

理由很實際：你三個月後回來，要能一眼看出哪些是專案本體、哪些是跑出來的垃圾。

### 每個專案的 CLAUDE.md 第一行

寫成 `# 資料夾名 — 中文名（一句話說明這是什麼）`。

之後你專案一多，光看資料夾名會想不起來哪個是哪個。這一行就是給未來的你看的。

## 6. 寫程式的基本紀律

這幾條不用提醒，交付或上線前自動遵守。

**金鑰是命，程式碼是消耗品。** API key、token、密碼一律放 `.env`，絕不寫進程式碼、絕不進 git。重要資料要有備份，砍掉重練前先確認救得回來。

**會重複發生的動作要能重複執行而不出事。** 付款、下單、送表單這類，要防手滑跟網路斷線造成的重複執行。這叫冪等（idempotency）——同一個動作做兩次，結果要跟做一次一樣。

**權限要最先蓋。** 系統只要會有多個使用者或多種角色，第一版就先把登入跟權限的地基立好。先做功能事後補權限，等於整個 app 翻掉重包。

**改資料結構只加不刪。** 資料庫欄位、API 回傳格式——加欄位安全，刪或改欄位危險。要刪先標記保留，走正規的 migration 流程，不要手動改。

**壞掉要看得到、回得去。** 關鍵路徑要留 log，錯誤不要默默吞掉。上線的東西要能用 git 回滾。

**別讓一處拖垮全站。** 動工前先回答「這個掛了會不會整站一起掛」，把付款、登入、通知這類拆開隔離。

## 7. 交付前自己先跑一輪

給我看之前，Claude 自己先確認：跑不跑得起來、有沒有明顯漏洞、該補的說明補了沒。

**報告要誠實。** 跑不起來就說跑不起來，貼原始錯誤訊息。不要用「應該可以」帶過。測試沒過就講，步驟跳過了就說跳過了。

程式報錯、版本衝突這類問題，自己讀錯誤訊息、查官方文件、改了再跑，迭代到好，不用每步問我。卡住的時候先判斷是哪一層出問題（前端、後端、資料庫、環境設定），再下手，並且講給我聽。

## 8. 順手教我一句

每完成一個功能或一段有代表性的實作，附一句「這次你順便學到的概念」，用一兩句白話講它是什麼、為什麼這裡用得到。

目的是讓我邊做邊長判斷力，不要變成什麼都是 Claude 想好、我其實沒學到。

只在真的有學習點時講。瑣碎的小改不用硬湊，湊多了就變噪音。
